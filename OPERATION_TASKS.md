# Операционные задачи Berg Sync

Документ описывает штатные задачи, которые выполняет `berg-sync`: полную
локальную миграцию, полную публикацию на хостинг, локальную дельту и
инкрементальную доставку на хостинг.

## 1. Конфигурация

Программа автоматически загружает `.env`. Основные параметры:

```dotenv
MDB_PATH="C:/WORK/BERG/Berg/DB/bergauto.mdb"

PG_LOCAL_CONNECTION_STRING="Host=localhost;Port=5432;Database=bergdb;..."
PG_HOSTING_CONNECTION_STRING="Host=pg4.sweb.ru;Port=5433;Database=...;SSL Mode=VerifyFull"

DELTA_PACKAGE_DIR="C:/WORK/berg_sync/delta-packages"

HOSTING_SSH_TARGET="bergvl"
HOSTING_TRANSFER_DIR="/home/d/debrskyru/berg-transfer"
HOSTING_RESTORE_SCRIPT="/home/d/debrskyru/berg-transfer/restore-hosting.sh"
```

Приоритет пути к MDB:

1. аргумент `--mdb`;
2. `MDB_PATH` из окружения;
3. `MDB_PATH` из `.env`.

Приоритет локального PostgreSQL:

1. аргумент `--pg`;
2. `PG_LOCAL_CONNECTION_STRING` из окружения;
3. `PG_LOCAL_CONNECTION_STRING` из `.env`.

`PG_HOSTING_CONNECTION_STRING` используется только при полной публикации или
при инкрементальном запуске с `--sync-hosting`.

## 2. Общая модель версий

Обе базы содержат состояние:

```text
baseline_id — идентификатор последней полной миграции
delta_seq   — номер применённой дельты внутри baseline
```

Пример:

```text
baseline_id = 2026-09-19-174505-full
delta_seq   = 3
```

Полная миграция создаёт новый baseline и устанавливает:

```text
delta_seq = 0
```

Каждая инкрементальная выгрузка увеличивает `delta_seq` на единицу, включая
запуск без фактических изменений.

Состояние хранится в:

```text
berg_sync.state
berg_sync.patches
berg_sync.patch_delivery
```

## 3. Задача: полная локальная миграция

### Команда PowerShell

```powershell
dotnet run --project . -- `
  --migrate `
  --confirm-drop
```

Для другой версии MDB:

```powershell
dotnet run --project . -- `
  --mdb "C:\path\to\previous.mdb" `
  --migrate `
  --confirm-drop
```

### Последовательность

1. Загружается `.env`.
2. Открывается MDB через ACE OLE DB.
3. Проверяется наличие целевой базы PostgreSQL.
4. Устанавливается `Asia/Vladivostok`.
5. Удаляются схемы:
   ```text
   bergauto
   bergapp
   berg_sync
   ```
6. Создаётся `bergauto`.
7. Через Binary COPY переносятся:
   ```text
   Bosses
   Cargos
   Cars
   Customers
   Tariffs
   xSaldo
   Applications
   XInvoices
   XInvoicePays
   XInvoiceDatas
   ```
8. Каждая таблица проверяется через `COUNT(*)`.
9. Создаются индексы и выполняется `ANALYZE`.
10. Устанавливается `hstore`.
11. Создаются `get_operations()` и `calculate_and_save_operations()`.
12. Полностью рассчитывается `bergapp.operations`.
13. Создаются materialized views.
14. Создаётся новый `berg_sync.state` с `delta_seq = 0`.
15. Сохраняются максимальные ID источника.

### Транзакционность

Каждая исходная таблица переносится в отдельной транзакции. Полная миграция в
целом не является одной транзакцией. При ошибке её нужно повторить полностью.

### Результат

После успешной миграции локальная база готова:

- к полной публикации;
- к локальным дельтам;
- к синхронным локальным и удалённым дельтам.

## 4. Задача: полная миграция и публикация на хостинг

### Команда PowerShell

```powershell
dotnet run --project . -- `
  --migrate `
  --confirm-drop `
  --publish-hosting `
  --confirm-hosting-restore
```

Для теста можно ускорить сжатие:

```powershell
--zstd-level 3
```

Штатное значение:

```text
--zstd-level 17
```

### Локальная подготовка

Сначала выполняется полная локальная миграция. Публикация начинается только
после её полного успеха.

Перед формированием dump проверяется:

- наличие `berg_sync.state`;
- `delta_seq = 0`;
- доступность PostgreSQL на хостинге;
- отсутствие recovery mode;
- корректность TLS-соединения.

### Формирование поставки

Создаётся directory-format dump схем:

```text
bergauto
bergapp
berg_sync
```

Затем формируется `manifest.json`, содержащий:

- `baseline_id`;
- `delta_seq`;
- время создания;
- исходную локальную базу;
- `COUNT(*)` всех таблиц и представлений;
- `MAX(ID)` таблиц с первичным ключом.

Структура поставки:

```text
bergdb-dump/
manifest.json
```

Она упаковывается в TAR и сжимается Zstandard:

```text
berg-transfer-<baseline-id>.tar.zst
```

Рядом создаётся SHA-256.

### SFTP-загрузка

Удалённый временный файл:

```text
berg-transfer-<baseline-id>.tar.zst.uploading
```

Алгоритм:

1. Если временного файла нет, используется `put`.
2. Если файл уже существует после обрыва, используется `reput`.
3. По умолчанию выполняется до 20 попыток.
4. Между попытками выдерживается пауза 3 секунды.
5. После загрузки SHA-256 вычисляется на сервере.
6. При совпадении файл атомарно переименовывается.
7. Создаётся удалённый checksum-файл.

### Удалённое восстановление

По SSH запускается:

```text
HOSTING_RESTORE_SCRIPT <archive-name>
```

Скрипт:

1. получает `flock`;
2. проверяет SHA-256;
3. выполняет `zstd --test`;
4. проверяет пути внутри TAR;
5. проверяет наличие `bergauto`, `bergapp`, `berg_sync` в dump;
6. проверяет базу, пользователя и recovery mode;
7. создаёт `hstore`, если расширение отсутствует;
8. выполняет:
   ```bash
   pg_restore --clean --if-exists --single-transaction
   ```
9. проверяет ключевые объекты и `berg_sync.state`;
10. требует `delta_seq = 0`;
11. вызывает `berg_persistent.archive_invoices()`;
12. записывает marker `<baseline-id>.restored`;
13. удаляет архив только после полного успеха.

Схема и процедура `berg_persistent` должны существовать заранее. Ошибка вызова
считается ошибкой публикации.

### Итоговая проверка

После restore локальная программа повторно подключается к хостингу и сравнивает:

- `baseline_id`;
- `delta_seq`;
- `COUNT(*)`;
- `MAX(ID)`;
- `bergapp.operations`;
- materialized views.

При несовпадении публикация считается неуспешной, даже если `pg_restore`
завершился без ошибки.

### Поведение при ошибке

- локальная полная миграция не публикуется, если она завершилась ошибкой;
- незавершённый SFTP-файл сохраняется для `reput`;
- архив на сервере сохраняется при ошибке restore;
- локальный рабочий каталог сохраняется;
- `pg_restore --single-transaction` откатывает замену схем при ошибке;
- после успешного restore архив удаляется.

## 5. Задача: публикация уже подготовленной локальной базы

### Команда

```powershell
dotnet run --project . -- `
  --publish-hosting `
  --confirm-hosting-restore
```

Операция разрешена только при:

```text
delta_seq = 0
```

Если локальная база уже получила дельты, для полной публикации нужно сначала
выполнить новую полную миграцию.

## 6. Задача: локальная инкрементальная выгрузка

### Команда

```powershell
dotnet run --project . -- `
  --incremental
```

### Что выбирается из MDB

- полностью: `Bosses`, `Cargos`, `Cars`, `Tariffs`;
- `XInvoices`: новые ID и последние 90 дней;
- `XInvoicePays`: новые ID, последние 90 дней и overlap 50 000;
- `XInvoiceDatas`: новые ID и overlap 20 000;
- `Applications`: новые ID и недавние даты;
- `Customers`: новые и связанные с выбранными заявками.

После первичной выборки достраиваются связи:

```text
платёж/позиция → счёт
счёт → заявка
счёт → все платежи и позиции
заявка → клиенты
```

### Сравнение

Кандидаты загружаются во временные таблицы PostgreSQL и сравниваются со строками
`bergauto` через `IS DISTINCT FROM` по всем бизнес-колонкам.

Новые и изменившиеся строки повторно читаются из MDB. Если первое и второе
чтение отличаются, строка откладывается до следующего запуска.

### Применение

В одной локальной транзакции:

1. выполняется upsert;
2. вычисляются финансовые пары;
3. пересчитывается `operations`;
4. обновляются materialized views;
5. вызывается `berg_persistent.archive_invoices()`;
6. записывается patch;
7. увеличивается `delta_seq`.

Удаления не применяются.

## 7. Задача: инкрементальная выгрузка локально и на хостинг

### Команда PowerShell

```powershell
dotnet run --project . -- `
  --incremental `
  --sync-hosting
```

### Неизменяемый пакет

Перед локальным commit создаётся каталог:

```text
<DELTA_PACKAGE_DIR>/<patch-id>/
```

Содержимое:

```text
package.json
package.sha256
```

Пакет содержит:

- `patch_id`;
- baseline;
- начальный и конечный `delta_seq`;
- путь к исходному MDB;
- период выборки;
- коррекцию дат;
- количество вставок и обновлений;
- строки всех изменившихся таблиц;
- затронутые финансовые пары;
- максимальные ID источника;
- политику удалений `ignore`.

После создания пакет не изменяется. Перед каждой доставкой проверяется SHA-256.

### Порядок применения

```text
создание пакета
→ локальный commit
→ удалённая транзакция
→ проверка удалённого state
→ статус applied
```

На хостинге:

1. проверяется `baseline_id`;
2. проверяется `from_delta_seq`;
3. получается advisory lock;
4. состояние проверяется повторно;
5. создаются временные staging-таблицы;
6. строки загружаются через Binary COPY;
7. выполняется upsert;
8. пересчитываются финансовые пары;
9. обновляются materialized views;
10. записывается patch;
11. устанавливается `to_delta_seq`;
12. транзакция фиксируется;
13. состояние проверяется после commit.

### Идемпотентность

Если соединение оборвалось после удалённого commit, повторная доставка проверит:

- `patch_id` уже существует;
- baseline совпадает;
- `delta_seq` уже равен `to_delta_seq`.

В этом случае пакет считается успешно применённым и повторный upsert не
выполняется.

### Pending и failed

Локальная таблица `berg_sync.patch_delivery` хранит состояния:

```text
local   applied
hosting pending | applying | applied | failed
```

В начале каждого запуска с `--sync-hosting` сначала доставляются все пакеты со
статусом `pending` или `failed`. Пока старая доставка не завершилась, новая
дельта не формируется.

Если пакет отсутствует или его SHA-256 не совпадает, запуск прекращается.

### Критичное эксплуатационное правило

После общей полной публикации нельзя чередовать режимы:

```text
--incremental
--incremental --sync-hosting
```

Локальный запуск без `--sync-hosting` увеличит только локальный `delta_seq`, и
состояния баз разойдутся. Если хостинг должен поддерживаться актуальным, каждый
штатный запуск нужно выполнять с `--sync-hosting`.

Локальный режим следует использовать только для отдельной тестовой базы или
когда последующая полная публикация гарантированно создаст новый baseline.

## 8. Задача: расширенная проверка Customers

Периодически следует выполнять:

```powershell
dotnet run --project . -- `
  --incremental `
  --sync-hosting `
  --full-customers
```

Этот режим полностью сравнивает `Customers`. Рекомендуемая частота — раз в
четыре часа.

## 9. Поведение удалений

Инкрементальная выгрузка не удаляет строки. Поэтому после дельты могут временно
оставаться записи, удалённые из MDB.

Это относится, в частности, к `Applications`. Локальная база и хостинг при этом
остаются одинаковыми, но могут отличаться от полной миграции нового MDB.

Удаления исправляются следующей полной миграцией.

`xSaldo` также обновляется только полной миграцией.

## 10. Рекомендуемое расписание

```text
Каждые 30 минут:
  --incremental --sync-hosting

Каждые 4 часа:
  --incremental --sync-hosting --full-customers

Ночью:
  --migrate --confirm-drop --publish-hosting --confirm-hosting-restore
```

Полная и инкрементальная задачи не должны выполняться одновременно.

## 11. Контроль успешности

Успешная полная публикация должна завершаться сообщениями:

```text
Полная публикация и проверка завершены успешно.
Baseline: <id>
```

Успешная удалённая дельта:

```text
Пакет <patch-id> применён на хостинге.
Тот же пакет применён на хостинге.
```

Дополнительно следует контролировать:

```sql
SELECT * FROM berg_sync.state;

SELECT patch_id, target, status, attempts, last_error, applied_at
FROM berg_sync.patch_delivery
ORDER BY patch_id, target;
```

## 12. Хранение и очистка файлов

Полные архивы:

- удаляются с хостинга после успешного restore;
- удаляются локально после успешной итоговой проверки;
- сохраняются при ошибке.

Delta-пакеты автоматически не удаляются. Рекомендуется хранить их не менее семи
дней и очищать только пакеты со статусом `applied` на обоих направлениях.

## 13. Ограничения

- MDB не читается как единый транзакционный снимок;
- удаления применяются только полной миграцией;
- `xSaldo` применяется только полной миграцией;
- refresh materialized views выполняется полностью;
- локальная и полная удалённая задачи пока запускаются вручную;
- автоматическое расписание и уведомления не реализованы;
- автоматическая очистка старых delta-пакетов не реализована.

## 14. Безопасность

- `.env` не добавляется в Git;
- Npgsql использует `SSL Mode=VerifyFull`;
- серверный libpq использует `PGSSLMODE=verify-full` и
  `PGSSLROOTCERT=system`;
- пароли не передаются в аргументах процессов;
- SFTP и SSH используют ключевую авторизацию;
- полная удалённая замена требует `--confirm-hosting-restore`;
- локальная полная миграция требует `--confirm-drop`;
- restore-конфигурация на хостинге должна иметь права `0600`.
