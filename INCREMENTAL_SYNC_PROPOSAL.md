# Предложение: периодическая инкрементальная выгрузка с ежедневной полной синхронизацией

## 1. Исходные условия

- структуру MDB менять нельзя;
- клиентские приложения менять нельзя;
- останавливать клиентские приложения нельзя;
- строгая транзакционная согласованность инкрементальной выгрузки не требуется;
- раз в сутки выполняется полная выгрузка, исправляющая возможные расхождения;
- локальный и удалённый PostgreSQL после полной выгрузки считаются идентичными;
- инкрементальные обновления применяются прямым подключением через Npgsql, при необходимости через SSH-туннель.

## 2. Цель

Между полными ночными выгрузками периодически передавать:

1. новые записи;
2. документы за заданный скользящий период;
3. фактически изменившиеся строки внутри выбранного множества;
4. связанные записи, необходимые для целостности;
5. список финансовых пар, которые нужно пересчитать.

Удаления в первой версии инкрементальной синхронизации предлагается **не применять**. Они будут исправляться ежедневной полной выгрузкой.

## 3. Общая схема

```text
Работающий MDB
      │
      │ чтение без эксклюзивной блокировки
      ▼
Кандидаты:
- новые ID
- документы за последние N дней
- связанные записи
      │
      ▼
Временная staging-схема локального PostgreSQL
      │
      │ сравнение с текущей bergauto
      ▼
DeltaPackage
      ├── новые строки
      ├── изменённые строки
      ├── affected_pairs
      └── manifest
      │
      ├── применение к локальному PostgreSQL
      └── применение к хостингу через Npgsql/SSH
```

Раз в сутки:

```text
Полная миграция MDB → локальный PostgreSQL
        ↓
Полный pg_dump → хостинг
        ↓
Новая базовая версия
```

## 4. Режимы синхронизации

### 4.1. Инкрементальный режим

Например, каждые 30 минут:

```bash
berg-sync delta \
  --period-days 90 \
  --id-overlap 10000
```

Особенности:

- не удаляет строки;
- передаёт только реальные изменения;
- может не обнаружить изменения старше периода;
- возможные пропуски исправляются ночью.

### 4.2. Полный режим

Например, ежедневно в 02:00:

```bash
berg-sync full
```

Полный режим:

- полностью перечитывает MDB;
- пересоздаёт локальную `bergauto`;
- пересчитывает `bergapp`;
- передаёт полную базу на хостинг;
- создаёт новую базовую версию;
- обнуляет последовательность инкрементальных пакетов.

## 5. Версия базовой копии

Рекомендуется разделить версию на две составляющие:

```text
baseline_id — идентификатор последней полной выгрузки;
delta_seq   — номер инкрементального обновления внутри baseline.
```

Например:

```text
baseline_id = 2026-09-18-full
delta_seq   = 3
```

После следующей полной выгрузки:

```text
baseline_id = 2026-09-19-full
delta_seq   = 0
```

### 5.1. Таблица состояния

```sql
CREATE SCHEMA IF NOT EXISTS berg_sync;

CREATE TABLE IF NOT EXISTS berg_sync.state (
    id integer PRIMARY KEY CHECK (id = 1),
    baseline_id text NOT NULL,
    delta_seq bigint NOT NULL,
    source_mdb text,
    updated_at timestamp NOT NULL DEFAULT current_timestamp
);
```

Пример начального состояния:

```sql
INSERT INTO berg_sync.state (
    id,
    baseline_id,
    delta_seq,
    source_mdb
)
VALUES (
    1,
    '2026-09-18-full',
    0,
    'bergauto.mdb'
);
```

Инкрементальный пакет содержит:

```json
{
  "patchId": "2026-09-18-full-delta-0001",
  "baselineId": "2026-09-18-full",
  "fromDeltaSeq": 0,
  "toDeltaSeq": 1
}
```

Пакет можно применить только к базе со следующим состоянием:

```text
baseline_id = 2026-09-18-full
delta_seq   = 0
```

## 6. Период выборки

Рекомендуется использовать скользящий период:

```text
сегодня - 90 дней
```

Например, при запуске 18 сентября:

```text
period_start = 2026-06-20 00:00:00
```

При каждом запуске перечитываются те же 90 дней. Это допустимо, поскольку фактически в дельту попадут только строки, отличающиеся от локального PostgreSQL.

### 6.1. Почему нужен большой период

Пользователь может изменить документ не в день его создания:

```text
счёт создан:  1 августа
исправлен:   15 сентября
```

Начальные параметры:

```text
период:       90 дней
частота:      каждые 30 минут
полная копия: раз в сутки
```

После накопления статистики период можно изменить.

## 7. Защита по ID

Кроме периода нужно выбирать новые записи по ID:

```sql
WHERE "ID" > last_max_id - id_overlap
```

Не рекомендуется использовать только:

```sql
WHERE "ID" > last_max_id
```

В работающей базе возможна ситуация:

1. транзакция получила ID 100;
2. другая транзакция получила ID 101 и завершилась раньше;
3. выгрузка увидела 101, но ещё не увидела 100;
4. checkpoint стал равен 101;
5. запись 100 была пропущена.

Поэтому вводится перекрытие:

```text
id_overlap = 10 000
```

Например:

```text
last_max_id = 800 000
читаем ID > 790 000
```

Повторные записи отфильтруются сравнением с PostgreSQL.

## 8. Правила выборки по таблицам

### 8.1. `XInvoices`

Первичные кандидаты:

```sql
SELECT *
FROM XInvoices
WHERE ID > ?
   OR Date >= ?;
```

Фактические условия:

```text
ID > last_max_id - id_overlap
OR Date >= period_start
```

Также в набор добавляются счета, на которые ссылаются выбранные платежи и позиции.

### 8.2. `XInvoicePays`

```sql
SELECT *
FROM XInvoicePays
WHERE ID > ?
   OR Date >= ?;
```

Для каждого выбранного платежа в набор включается связанный счёт:

```text
XInvoicePays.ID_XInvoice → XInvoices.ID
```

Практическое сравнение двух последовательных MDB показало исправления старых
платежей, которые не попадали ни в период 90 дней, ни в общее перекрытие 10 000 ID.
Поэтому для `XInvoicePays` рекомендуется отдельное увеличенное перекрытие:

```text
payment_id_overlap = 50 000
```

Кроме того, после формирования набора счетов следует перечитать **все платежи
выбранных счетов**. Это позволяет получить согласованный набор платежей при
изменении `XInvoices.Pays` и обнаружить исправление старого платежа, если его
счёт попал в выборку по другому признаку.

### 8.3. `XInvoiceDatas`

У позиций нет собственной даты документа. Выбираются:

1. новые ID с перекрытием;
2. все позиции выбранных счетов.

Вторая часть обязательна не только для новых счетов: за сутки наблюдались
изменения количества, стоимости и порядка позиций уже существующих счетов.

```sql
SELECT *
FROM XInvoiceDatas
WHERE ID > ?
   OR ID_XInvoice IN (...);
```

Если новая позиция добавлена к старому счёту, она попадёт по ID, а связанный счёт будет добавлен в набор.

### 8.4. `Applications`

Выбираются:

1. новые ID с перекрытием;
2. заявки выбранных счетов;
3. заявки с недавней регистрацией или работой.

```sql
SELECT *
FROM Applications
WHERE ID > ?
   OR DateReg >= ?
   OR DateWorkIn >= ?
   OR DateWorkOut >= ?
   OR ID IN (...application IDs from invoices...);
```

Для nullable-дат нужны отдельные условия.

### 8.5. `Customers`

Выбираются:

1. новые ID с перекрытием;
2. все клиенты, на которых ссылаются выбранные заявки:

```text
ID_Customer
ID_CustomerOut
ID_CustomerPay
```

Старый клиент также попадёт в дельту, если участвует в новом или недавнем документе.

Изменение старого клиента, не связанного с выбранными документами, будет обнаружено ночной полной выгрузкой.

Практический замер показал изменение старого клиента и появление 16 новых
клиентов за сутки. Таблица содержит около 67 тысяч строк, поэтому дополнительно
рекомендуется выполнять её полный сравнительный проход раз в 4 часа. В обычной
30-минутной дельте достаточно новых ID и клиентов из замыкания связей.

### 8.6. Маленькие справочники

Следующие таблицы рекомендуется читать полностью при каждом инкрементальном запуске:

- `Bosses` — около 16 строк;
- `Cargos` — около 3 800 строк;
- `Cars` — около 630 строк;
- `Tariffs` — около 113 строк.

В дельту попадут только реально отличающиеся записи.

### 8.7. `xSaldo`

У таблицы нет надёжного первичного ключа.

Для первой версии рекомендуется:

- не обновлять её инкрементально;
- обновлять только ночной полной миграцией.

Если `xSaldo` необходима на хостинге в течение дня, можно передавать её целиком, но для точной синхронизации потребуется определить составной ключ.

## 9. Формирование замкнутого набора данных

Выборка выполняется итеративно.

### Шаг 1. Первичные кандидаты

```text
recent/new XInvoices
recent/new XInvoicePays
new XInvoiceDatas
recent/new Applications
```

### Шаг 2. Расширение связей

Из выбранных платежей и позиций получить `ID_XInvoice`:

```text
XInvoicePays → XInvoices
XInvoiceDatas → XInvoices
```

### Шаг 3. Получить заявки

```text
XInvoices.ID_Application → Applications.ID
```

### Шаг 4. Получить справочники

```text
Applications.ID_Customer
Applications.ID_CustomerOut
Applications.ID_CustomerPay
Applications.ID_Cargo
Applications.ID_Tariff

XInvoices.ID_Boss

XInvoiceDatas.ID_Car
```

### Шаг 5. Обратно расширить состав документа

После получения окончательного набора счетов повторно выбираются:

```text
все XInvoicePays выбранных счетов
все XInvoiceDatas выбранных счетов
```

Это важно для фактической модели изменений: новый платеж меняет старый счёт,
а исправление может затронуть старый платеж или позицию.

### Шаг 6. Повторить расширение

Если появились дополнительные счета или заявки, расширение повторяется до тех пор, пока набор ID не перестанет изменяться. Для текущих связей обычно достаточно двух проходов.

## 10. Загрузка кандидатов в staging

Локально создаётся отдельная схема:

```sql
CREATE SCHEMA berg_delta_build_0001;
```

Таблицы можно сделать `UNLOGGED`:

```sql
CREATE UNLOGGED TABLE berg_delta_build_0001."XInvoices"
(LIKE bergauto."XInvoices" INCLUDING ALL);
```

Кандидаты из MDB загружаются через Binary COPY.

Должна применяться та же политика дат, что и в базовой PostgreSQL:

```text
--mdb-date-offset-hours
```

Если полная база была создана с вычитанием 10 часов, дельта обязана использовать точно такое же преобразование.

## 11. Определение фактических изменений

Выборка за 90 дней может содержать десятки тысяч строк, но большинство уже находится в PostgreSQL.

### 11.1. Новые записи

```sql
SELECT incoming.*
FROM berg_delta_build_0001."XInvoices" incoming
LEFT JOIN bergauto."XInvoices" current
  ON current."ID" = incoming."ID"
WHERE current."ID" IS NULL;
```

### 11.2. Изменённые записи

```sql
SELECT incoming.*
FROM berg_delta_build_0001."XInvoices" incoming
JOIN bergauto."XInvoices" current
  ON current."ID" = incoming."ID"
WHERE ROW(
    current."ID_Application",
    current."Nomer",
    current."Date",
    current."Cost",
    current."IsFixed",
    current."Pays",
    current."Name",
    current."Mem",
    current."ID_Boss",
    current."IsUseSecondAccount",
    current."BaseCode",
    current."ID_Ref",
    current."ToExport"
) IS DISTINCT FROM ROW(
    incoming."ID_Application",
    incoming."Nomer",
    incoming."Date",
    incoming."Cost",
    incoming."IsFixed",
    incoming."Pays",
    incoming."Name",
    incoming."Mem",
    incoming."ID_Boss",
    incoming."IsUseSecondAccount",
    incoming."BaseCode",
    incoming."ID_Ref",
    incoming."ToExport"
);
```

Сравниваются все бизнес-колонки.

## 12. Политика удалений

При чтении работающего MDB отсутствие строки может быть временным эффектом непоследовательного чтения.

Для частой инкрементальной выгрузки рекомендуется:

```text
INSERT — применять
UPDATE — применять
DELETE — не применять
```

Удалённые строки останутся в PostgreSQL до ночной полной синхронизации.

### 12.1. Причина

Ложный `UPDATE` обычно исправится следующим запуском. Ложный `DELETE` может:

- удалить счёт;
- удалить позиции;
- изменить задолженность;
- убрать документ с хостинга;
- потребовать сложного восстановления.

Безопаснее временно оставить удалённую запись, чем ошибочно удалить актуальную.

### 12.2. Возможное расширение

Удаление можно применять только после подтверждения в нескольких запусках:

```text
первый запуск: missing_count = 1
второй запуск: missing_count = 2
третий запуск: missing_count = 3 → удалить
```

Для первой версии это не требуется.

## 13. Проверка стабильности изменившихся строк

После определения фактически изменившихся строк рекомендуется повторно прочитать их из MDB:

```text
Первое чтение → hash A
Повторное чтение → hash B
```

Если:

```text
hash A == hash B
```

строка включается в дельту.

Если:

```text
hash A != hash B
```

строка откладывается до следующего запуска.

Это не даёт строгой транзакционной согласованности, но снижает вероятность передачи промежуточного состояния.

## 14. DeltaPackage

После сравнения создаётся неизменяемый пакет:

```text
delta/
└── 2026-09-18-full-delta-0001/
    ├── manifest.json
    ├── Bosses.dat
    ├── Cargos.dat
    ├── Cars.dat
    ├── Customers.dat
    ├── Tariffs.dat
    ├── Applications.dat
    ├── XInvoices.dat
    ├── XInvoicePays.dat
    ├── XInvoiceDatas.dat
    ├── affected-pairs.dat
    └── sha256.txt
```

Возможные форматы данных:

- MessagePack;
- JSON Lines;
- CSV;
- собственный бинарный формат.

Для небольших дельт достаточно JSON Lines с последующим zstd. Для быстрой загрузки можно использовать MessagePack.

### 14.1. Manifest

```json
{
  "patchId": "2026-09-18-full-delta-0001",
  "baselineId": "2026-09-18-full",
  "fromDeltaSeq": 0,
  "toDeltaSeq": 1,
  "createdAt": "2026-09-18T12:30:00+10:00",
  "periodStart": "2026-06-20T00:00:00",
  "idOverlap": 10000,
  "deletePolicy": "ignore",
  "tables": {
    "Applications": {
      "upserts": 15
    },
    "XInvoices": {
      "upserts": 8
    },
    "XInvoicePays": {
      "upserts": 3
    },
    "XInvoiceDatas": {
      "upserts": 22
    }
  },
  "affectedPairs": 4
}
```

Пакет нельзя изменять после генерации.

## 15. Вычисление затронутых финансовых пар

Для изменившихся счетов определяется:

```text
id_seller = XInvoices.ID_Boss
id_payer  = Applications.ID_CustomerPay
```

Если изменился `ID_Boss`, нужно включить старую и новую пары.

Если изменился `ID_CustomerPay` в заявке, также включаются старая и новая пары.

Пример:

```text
до изменения:    seller=3, payer=100
после изменения: seller=3, payer=200
```

В пакет включаются:

```text
(3, 100)
(3, 200)
```

Для платежей затрагивается пара связанного счёта. Список пар должен быть уникальным.

## 16. Применение дельты

Один и тот же `DeltaPackage` применяется:

1. к локальному PostgreSQL;
2. к PostgreSQL на хостинге.

### 16.1. Последовательность

```text
1. Проверить baseline_id и delta_seq.
2. Получить advisory lock.
3. Начать транзакцию.
4. Создать временные staging-таблицы.
5. Загрузить данные Binary COPY.
6. Выполнить upsert.
7. Пересчитать affected_pairs.
8. Обновить materialized views.
9. Проверить результат.
10. Обновить delta_seq.
11. Зафиксировать транзакцию.
```

### 16.2. Upsert

```sql
INSERT INTO bergauto."XInvoices" AS target
SELECT *
FROM temp_delta_xinvoices
ON CONFLICT ("ID") DO UPDATE
SET
    "ID_Application" = EXCLUDED."ID_Application",
    "Nomer" = EXCLUDED."Nomer",
    "Date" = EXCLUDED."Date",
    "Cost" = EXCLUDED."Cost",
    "IsFixed" = EXCLUDED."IsFixed",
    "Pays" = EXCLUDED."Pays",
    "Name" = EXCLUDED."Name",
    "Mem" = EXCLUDED."Mem",
    "ID_Boss" = EXCLUDED."ID_Boss"
WHERE ROW(
    target."ID_Application",
    target."Nomer",
    target."Date",
    target."Cost",
    target."IsFixed",
    target."Pays",
    target."Name",
    target."Mem",
    target."ID_Boss"
) IS DISTINCT FROM ROW(
    EXCLUDED."ID_Application",
    EXCLUDED."Nomer",
    EXCLUDED."Date",
    EXCLUDED."Cost",
    EXCLUDED."IsFixed",
    EXCLUDED."Pays",
    EXCLUDED."Name",
    EXCLUDED."Mem",
    EXCLUDED."ID_Boss"
);
```

## 17. Пересчёт операций

Для каждой затронутой пары:

```sql
CALL bergapp.calculate_and_save_operations(
    p_id_payer,
    p_id_seller
);
```

Используется исправленная детерминированная версия `get_operations()`.

Если затронутых пар слишком много, выгоднее выполнить полный пересчёт:

```sql
CALL bergapp.calculate_and_save_operations();
```

Предлагаемый начальный порог:

```text
до 500 affected_pairs → частичный пересчёт;
больше 500            → полный пересчёт.
```

Порог необходимо уточнить по замерам.

## 18. Materialized views

Для первой версии после каждой дельты можно выполнять полный refresh:

```sql
REFRESH MATERIALIZED VIEW bergapp.payers;
REFRESH MATERIALIZED VIEW bergapp.sellers;
REFRESH MATERIALIZED VIEW bergapp.invoices;
REFRESH MATERIALIZED VIEW bergapp.counterparties;
REFRESH MATERIALIZED VIEW bergapp.balances;
REFRESH MATERIALIZED VIEW bergapp.debt_invoices;
```

Это проще и безопаснее.

Если refresh займёт слишком много времени:

- `payers`, `sellers`, `counterparties` можно оставить полными;
- `invoices`, `balances`, `debt_invoices` позже заменить таблицами с точечным обновлением.

## 19. Порядок доставки

Рекомендуется сначала применять пакет локально:

```text
1. Сформировать пакет.
2. Применить локально.
3. Проверить локальную базу.
4. Применить на хостинге.
5. Проверить хостинг.
6. Отметить пакет доставленным в обе базы.
```

Если локальное применение успешно, а хостинг недоступен:

```text
local:   applied
hosting: pending
```

Нельзя создавать следующий пакет, пока предыдущий не применён на хостинге. Иначе локальная база перестанет быть общей базовой версией.

Пакет сохраняется для повторной отправки.

## 20. Таблицы доставки

```sql
CREATE TABLE berg_sync.patches (
    patch_id text PRIMARY KEY,
    baseline_id text NOT NULL,
    from_delta_seq bigint NOT NULL,
    to_delta_seq bigint NOT NULL,
    period_start timestamp NOT NULL,
    checksum text NOT NULL,
    created_at timestamp NOT NULL,
    status text NOT NULL
);

CREATE TABLE berg_sync.patch_delivery (
    patch_id text NOT NULL,
    target text NOT NULL,
    status text NOT NULL,
    attempts integer NOT NULL DEFAULT 0,
    last_error text,
    applied_at timestamp,
    PRIMARY KEY (patch_id, target)
);
```

Пример:

```text
patch_id                        target    status
------------------------------  --------  -------
2026-09-18-full-delta-0001      local     applied
2026-09-18-full-delta-0001      hosting   pending
```

## 21. Ежедневная полная выгрузка

### 21.1. Последовательность

```text
1. Заблокировать запуск новых delta-задач.
2. Доставить все pending-пакеты или отменить их.
3. Выполнить полную миграцию MDB → локальный PostgreSQL.
4. Рассчитать operations и views.
5. Проверить локальную базу.
6. Передать полный dump на хостинг.
7. Проверить хостинг.
8. Создать новый baseline_id.
9. Установить delta_seq = 0.
10. Удалить пакеты предыдущего baseline.
11. Разрешить инкрементальные задачи.
```

Новая полная база получает состояние:

```text
baseline_id = 2026-09-19-full
delta_seq   = 0
```

Пакеты от предыдущего baseline после этого применять нельзя.

### 21.2. Ограничение полной выгрузки

Полная миграция из работающего MDB также не является строгим транзакционным снимком. Но она полностью перечитывает источник и регулярно устраняет накопившиеся расхождения. Для принятого уровня eventual consistency это считается допустимым.

## 22. Защитные ограничения

Инкрементальный пакет не следует применять автоматически, если:

```text
изменено более 100 000 строк;
изменено более 20% таблицы;
затронуто более 5 000 пар;
MAX(ID) неожиданно уменьшился;
MAX(DateReg/Date) существенно меньше предыдущего значения;
счётчики Settings.NextAppNomer/NextTaskNomer откатились назад;
одновременно уменьшились MAX(ID) нескольких транзакционных таблиц;
появились массовые NULL в обязательных полях;
не читается одна из таблиц;
появились дубли ID;
обнаружена неправильная версия базы;
предыдущий пакет не доставлен на хостинг.
```

Проверка свежести источника должна выполняться **до чтения кандидатов**. Сравнение
реальных MDB обнаружило файл с более поздним временем изменения, но более старым
логическим состоянием: меньшими `MAX(ID)`, датами и счётчиками. Если применить из
такого файла обычные `UPDATE`, база на хостинге будет частично откачена назад.
Такой источник должен помечаться `stale_source`, а дельта — отклоняться.

В таком случае:

```text
delta помечается rejected;
ожидается ночная полная синхронизация.
```

## 23. Мониторинг

Для каждого запуска сохраняются:

- время начала и окончания;
- `period_start`;
- максимальные ID;
- число прочитанных кандидатов;
- число фактических изменений;
- число нестабильных строк;
- число `affected_pairs`;
- время применения локально;
- время применения на хостинге;
- время пересчёта `operations`;
- время refresh materialized views;
- ошибки.

Пример отчёта:

```text
Patch:                    2026-09-18-full-delta-0001
Период:                   90 дней
Кандидатов XInvoices:     24 350
Изменено XInvoices:       8
Новых XInvoices:          2
Изменено Applications:    5
Изменено XInvoicePays:    3
Изменено XInvoiceDatas:   22
Нестабильных строк:       1
Affected pairs:           4
Local apply:              3.2 сек
Hosting apply:            4.8 сек
```

## 24. Предлагаемые параметры первой версии

```text
Частота основной delta:             каждые 30 минут
Период повторной выборки:           90 дней
Общий ID overlap:                   10 000
XInvoicePays ID overlap:            50 000
XInvoiceDatas ID overlap:           20 000
Полный проход Customers:            каждые 4 часа
Полный проход малых справочников:   каждые 30 минут
Удаления:                            не применять
Повторная проверка изменений:       включена
Нестабильные строки:                отложить
Частичный пересчёт:                 до 500 пар
Полный refresh views:               включён
Полная синхронизация:               ежедневно
Хранение delta-пакетов:             7 дней
```

Перекрытия должны быть отдельными для каждой таблицы и храниться в manifest.
После нескольких недель мониторинга их следует уточнить по фактическому
расстоянию между текущим `MAX(ID)` и минимальным ID изменённой строки.

## 25. Ограничения решения

Инкрементальная выгрузка может временно не обнаружить:

- изменение документа старше периода;
- удаление;
- изменение старого клиента, не связанного с недавним документом;
- изменение строки во время её чтения;
- изменение `xSaldo`.

Эти расхождения исправляет ежедневная полная выгрузка.

Также возможны кратковременные логические несоответствия между связанными строками, если они изменяются одновременно с чтением. Повторная проверка и следующая delta-выгрузка уменьшают этот период.

## 26. Результаты проверки на суточных данных

Были сравнены две реальные версии MDB. Логически более новая версия содержала
следующие изменения в таблицах, входящих в текущую миграцию:

| Таблица | Добавлено | Удалено | Изменено |
|---|---:|---:|---:|
| `Applications` | 154 | 7 | 211 |
| `Bosses` | 0 | 0 | 3 |
| `Cars` | 0 | 0 | 1 |
| `Customers` | 16 | 0 | 1 |
| `XInvoices` | 196 | 0 | 159 |
| `XInvoicePays` | 178 | 0 | 3 |
| `XInvoiceDatas` | 367 | 0 | 4 |

`Cargos`, `Tariffs` и `xSaldo` за этот период не изменились.

Основные типы изменений:

- у 165 заявок изменился `Stage`;
- у заявок массово менялись плановые даты;
- у 159 существующих счетов изменился `Pays`;
- появились платежи для уже существующих счетов;
- исправлялись старые платежи, включая дату платежа;
- у позиций менялись `Amount`, `Cost` и `Pos`;
- менялись счётчики `Bosses.NextInvoiceNomer`;
- был изменён старый клиент и автомобиль.

Также ежедневно изменялись таблицы, которые сейчас не входят в полную миграцию:
`AppSubs`, `Credits`, `CustomersPoints`, `Plans`, `Settings` и `Tasks`. Их не
следует молча считать синхронизированными. Если они потребуются приложению на
хостинге, для них нужно отдельно определить связи, ключи и правила пересчёта.
До этого они остаются явно вне границ синхронизации.

### 26.1. Выводы для алгоритма

1. Объём суточной дельты небольшой; пакет из сотен строк практичнее полного dump.
2. Одного фильтра по дате недостаточно: исправлялись документы старше 90 дней.
3. Общего перекрытия 10 000 недостаточно для `XInvoicePays`.
4. Замыкание должно идти в обе стороны: платеж/позиция → счёт и счёт → все его
   платежи/позиции.
5. Изменение `XInvoices.Pays` требует пересчёта финансовой пары, даже если сам
   платеж по первичной выборке не найден.
6. Реальные удаления существуют, но при суточной полной синхронизации безопаснее
   по-прежнему не применять их в дельте.
7. Время изменения и имя MDB не доказывают свежесть данных; необходим логический
   freshness gate по нескольким таблицам.
8. Для гарантированного обнаружения произвольного изменения старой строки без
   `updated_at` всё равно нужен полный проход. Поэтому широкие проверки следует
   сочетать с ежедневной полной синхронизацией, а не пытаться бесконечно
   увеличивать период основной дельты.

### 26.2. Рекомендуемый двухуровневый график

```text
каждые 30 минут:
  новые ID + период 90 дней + табличные overlap + замыкание связей

каждые 4 часа:
  всё выше + полный сравнительный проход Customers
  + сбор статистики минимального изменённого ID

раз в сутки:
  полная миграция и новая baseline
```

## 28. Итог

При заданных ограничениях рекомендуется следующая практическая схема:

```text
проверка логической свежести MDB
+ новые ID с отдельным overlap для каждой таблицы
+ скользящий период 90 дней
+ двустороннее замыкание документов, платежей и позиций
+ периодические полные проходы Customers и малых справочников
+ сравнение с локальным PostgreSQL
+ только INSERT/UPDATE
+ прямое применение через Npgsql
+ ежедневная полная синхронизация
```

Решение не гарантирует моментальную транзакционную целостность, но обеспечивает быстрые обновления в течение дня и регулярное автоматическое исправление расхождений полной ночной выгрузкой.
