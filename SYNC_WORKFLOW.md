# Полная и инкрементальная выгрузка MDB → PostgreSQL

Документ описывает фактически реализованное поведение `berg-sync`. Это не план
будущей реализации: ниже перечислены текущие режимы, порядок операций,
транзакционные границы и известные ограничения.

## 1. Назначение

Программа переносит данные из Microsoft Access MDB в локальный PostgreSQL двумя
способами:

- **полная миграция** (`--migrate`) — заново создаёт основную часть базы;
- **инкрементальная выгрузка** (`--incremental` или `--delta`) — находит новые и
  изменившиеся строки и применяет только их.

Оба режима только читают MDB. Файл Access не изменяется.

Текущая инкрементальная реализация работает только с локальным PostgreSQL.
Отправки пакетов или прямого подключения к PostgreSQL на хостинге в ней нет.

## 2. Общая модель данных

Полная миграция переносит следующие таблицы в схему `bergauto`:

1. `Bosses`;
2. `Cargos`;
3. `Cars`;
4. `Customers`;
5. `Tariffs`;
6. `xSaldo`;
7. `Applications`;
8. `XInvoices`;
9. `XInvoicePays`;
10. `XInvoiceDatas`.

Структура таблиц, порядок колонок, первичные ключи и индексы берутся из
`migration-schema.json`. Этот файл генерируется из `schema.config.mjs`:

```bash
node generate-migration-schema.mjs
```

После переноса исходных таблиц создаются расчётные объекты схемы `bergapp`:

- `operations`;
- функция `get_operations()`;
- процедура `calculate_and_save_operations()`;
- materialized views `payers`, `sellers`, `invoices`, `counterparties`,
  `balances`, `debt_invoices`.

Схема `berg_persistent` содержит постоянные объекты архива и не удаляется полной
миграцией.

## 3. Преобразование дат

Access хранит даты без информации о часовом поясе. При записи в PostgreSQL из
каждой даты вычитается значение `--mdb-date-offset-hours`:

```text
дата PostgreSQL = дата MDB - mdb-date-offset-hours
```

По умолчанию вычитается 10 часов:

```bash
--mdb-date-offset-hours 10
```

Результат записывается как `timestamp without time zone`.

Полная и все последующие инкрементальные выгрузки обязаны использовать одно и
то же значение. Инкрементальный режим сохраняет его в `berg_sync.state` и
отклоняет запуск при несовпадении.

## 4. Полная миграция

### 4.1. Запуск

```bash
export PG_CONNECTION_STRING='Host=localhost;Port=5432;Database=postgres;Username=postgres;Password=secret'

dotnet run --project . -- \
  --mdb C:/WORK/BERG/Berg/DB/bergauto.mdb \
  --migrate \
  --pg-database bergdb \
  --pg-admin-database postgres \
  --mdb-date-offset-hours 10 \
  --confirm-drop
```

`--confirm-drop` обязателен. Без него программа завершится до изменения базы.

### 4.2. Подготовка базы

Программа:

1. подключается к административной базе, заданной через
   `--pg-admin-database`;
2. создаёт целевую базу, если её ещё нет;
3. устанавливает для неё часовой пояс `Asia/Vladivostok`;
4. подключается к целевой базе;
5. устанавливает расширение `hstore`, если оно отсутствует.

Затем удаляются:

```sql
DROP SCHEMA IF EXISTS berg_sync CASCADE;
DROP SCHEMA IF EXISTS bergauto CASCADE;
DROP SCHEMA IF EXISTS bergapp CASCADE;
```

Удаление `berg_sync` означает, что предыдущий baseline и история локальных
дельт становятся недействительными. Следующая инкрементальная выгрузка создаст
новый baseline.

Схема `berg_persistent` при этом сохраняется.

### 4.3. Создание и заполнение `bergauto`

Схема `bergauto` создаётся заново. Для каждой таблицы из
`migration-schema.json` выполняются следующие действия:

1. создаётся таблица с настроенными типами и первичным ключом;
2. из MDB читаются только перечисленные в конфигурации колонки;
3. значения приводятся к типам PostgreSQL;
4. данные загружаются через бинарный `COPY`;
5. сравнивается количество прочитанных и записанных строк;
6. транзакция таблицы фиксируется только после успешной проверки.

Каждая таблица переносится в отдельной транзакции. Это защищает отдельную
таблицу от частичной записи, но вся полная миграция не является одной общей
транзакцией. Если процесс завершится ошибкой в середине, база может содержать
уже перенесённые таблицы и не содержать последующие. Такой запуск нужно
повторить полностью.

Параметр:

```bash
--migration-limit N
```

ограничивает количество строк каждой таблицы и предназначен для диагностики.
Значение `0` означает перенос всех строк.

### 4.4. Индексы и статистика

После загрузки всех таблиц создаются индексы из `migration-schema.json`, затем
для каждой таблицы выполняется `ANALYZE`.

Для `bergapp.operations` отдельно создаётся индекс:

```sql
CREATE INDEX operations_payer_seller_idx
ON bergapp.operations (id_payer, id_seller);
```

Он нужен прежде всего для быстрого удаления и повторного расчёта отдельных
финансовых пар в инкрементальном режиме.

### 4.5. Расчёт операций

После подготовки `bergauto` устанавливаются функция и процедура расчёта, затем
выполняется полный пересчёт:

```sql
CALL bergapp.calculate_and_save_operations();
```

Процедура очищает `bergapp.operations` через `TRUNCATE` и одним запросом
рассчитывает операции для всех плательщиков и продавцов.

### 4.6. Представления и постоянные объекты

После расчёта операций создаются materialized views и объекты
`berg_persistent`.

Полная миграция считается завершённой только после успешной установки всех этих
объектов.

## 5. Инкрементальная выгрузка

### 5.1. Предварительное условие

Перед первой инкрементальной выгрузкой должна быть выполнена полная миграция.
Инкрементальный режим не создаёт таблицы `bergauto` и не может работать с
пустой базой.

Пример:

```bash
export PG_CONNECTION_STRING='Host=localhost;Port=5432;Database=postgres;Username=postgres;Password=secret'

dotnet run --project . -- \
  --mdb C:/WORK/BERG/Berg/DB/bergauto.mdb \
  --incremental \
  --pg-database bergdb \
  --mdb-date-offset-hours 10
```

`--delta` является алиасом `--incremental`.

### 5.2. Основные принципы

Инкрементальная выгрузка:

- применяет `INSERT` и `UPDATE`;
- не применяет `DELETE`;
- перечитывает перекрывающиеся диапазоны ID;
- перечитывает документы за скользящий период;
- сравнивает все бизнес-колонки;
- перед записью повторно читает изменившиеся строки из MDB;
- выполняет изменения PostgreSQL в одной транзакции;
- пересчитывает только затронутые финансовые пары, если их не слишком много;
- полностью обновляет materialized views;
- не взаимодействует с хостингом.

### 5.3. Проверка свежести MDB

До чтения кандидатов программа сравнивает максимальные ID в MDB и PostgreSQL
для таблиц:

- `Customers`;
- `Applications`;
- `XInvoices`;
- `XInvoicePays`;
- `XInvoiceDatas`.

Если хотя бы один максимальный ID в MDB меньше соответствующего значения в
PostgreSQL, источник считается логически более старым, и выгрузка отклоняется.
Это защищает от частичного отката базы при случайном выборе старой копии MDB.

Время изменения файла и дата в имени файла сами по себе не считаются
доказательством свежести.

Проверка по максимальным ID не обнаруживает все возможные варианты логического
отката, например изменение старых строк при неизменных максимальных ID. Поэтому
она является защитным минимумом, а не полной проверкой версии источника.

### 5.4. Скользящий период

По умолчанию используется период 90 дней:

```bash
--period-days 90
```

Начало периода вычисляется от локальной текущей даты:

```text
period_start = сегодня 00:00 - period_days
```

По датам выбираются:

- `XInvoices.Date`;
- `XInvoicePays.Date`;
- `Applications.DateReg`;
- `Applications.DateWorkIn`;
- `Applications.DateWorkOut`.

Период позволяет обнаруживать изменения недавних документов даже при
неизменном ID.

### 5.5. Перекрытия ID

Кроме периода повторно проверяются последние диапазоны ID:

```text
общий overlap:             10 000
XInvoicePays overlap:      50 000
XInvoiceDatas overlap:     20 000
```

Условие строится относительно максимального ID в PostgreSQL:

```text
ID > MAX(ID в PostgreSQL) - overlap
```

Например, при `MAX(ID) = 800000` и overlap `50000` будут повторно прочитаны
строки с `ID > 750000`.

Это не означает, что все прочитанные строки будут обновлены. Они сначала
сравниваются с PostgreSQL, и совпадающие строки отбрасываются.

Отдельное большое перекрытие платежей выбрано потому, что в реальных версиях
MDB встречались исправления старых платежей за пределами последних 10 000 ID.
Все значения можно изменить:

```bash
--id-overlap 10000
--payment-id-overlap 50000
--invoice-data-id-overlap 20000
```

### 5.6. Первичные кандидаты

Сначала читаются:

- все строки `Bosses`, `Cargos`, `Cars`, `Tariffs`;
- новые и недавние `XInvoices`;
- новые и недавние `XInvoicePays`;
- новые `XInvoiceDatas` с заданным перекрытием;
- новые и недавние `Applications`.

Малые справочники читаются полностью, но в дельту попадают только реально
изменившиеся строки.

### 5.7. Замыкание связей

После первичной выборки набор расширяется:

1. из выбранных платежей и позиций собираются `ID_XInvoice`;
2. загружаются соответствующие счета;
3. из счетов собираются `ID_Application`;
4. загружаются соответствующие заявки;
5. для итогового множества счетов повторно читаются **все** платежи и позиции;
6. из заявок собираются `ID_Customer`, `ID_CustomerOut`, `ID_CustomerPay`;
7. загружаются соответствующие клиенты.

Обратное чтение всех платежей и позиций выбранного счёта необходимо, чтобы
состав документа сравнивался целиком, а не только по новым ID.

По умолчанию `Customers` выбираются по новым ID и связям с заявками. Параметр:

```bash
--full-customers
```

заставляет сравнить таблицу `Customers` полностью. Такой проход можно запускать
реже, например раз в четыре часа.

### 5.8. Staging-таблицы

После чтения MDB начинается транзакция PostgreSQL и берётся advisory lock. Он не
позволяет двум процессам одновременно применять локальную дельту.

Для каждой синхронизируемой таблицы создаётся временная staging-таблица вида:

```text
delta_bosses
delta_customers
delta_applications
delta_xinvoices
...
```

Структура копируется из соответствующей таблицы `bergauto`. Кандидаты
загружаются в staging через Binary COPY с тем же преобразованием дат, что и при
полной миграции.

`xSaldo` в staging не загружается и инкрементально не обновляется, потому что у
неё нет надёжного первичного ключа.

### 5.9. Определение фактических изменений

Каждая staging-строка сравнивается с текущей строкой `bergauto` по `ID`:

- строки без соответствующего ID считаются новыми;
- для существующих ID все остальные колонки сравниваются через
  `IS DISTINCT FROM`;
- это сравнение корректно учитывает `NULL`.

Таким образом, десятки тысяч повторно прочитанных кандидатов могут дать лишь
несколько реальных изменений.

### 5.10. Повторная проверка стабильности

Новые и изменившиеся строки второй раз читаются из MDB по ID.

Если первое и второе чтение полностью совпадают, строка остаётся в staging. Если
значение изменилось между чтениями или строка исчезла, она считается
нестабильной и удаляется из текущей дельты. Следующий запуск попробует обработать
её снова.

Это не создаёт транзакционный снимок MDB, но уменьшает вероятность записи в
PostgreSQL промежуточного состояния активно изменяемого документа.

### 5.11. Защитный лимит

По умолчанию одна дельта не может изменить более 100 000 строк:

```bash
--delta-max-changes 100000
```

Если лимит превышен, транзакция откатывается. Параметр защищает от случайного
массового изменения из-за неверного источника или конфигурации.

### 5.12. Вычисление финансовых пар

Для изменившихся счетов, платежей, позиций и заявок определяется набор пар:

```text
(id_payer, id_seller)
```

где:

- `id_seller = XInvoices.ID_Boss`;
- `id_payer = Applications.ID_CustomerPay`.

Учитываются старые и новые варианты связей. Например, при изменении плательщика
заявки в набор попадают и прежняя, и новая финансовые пары.

### 5.13. Upsert

Данные применяются командой `INSERT ... ON CONFLICT (ID) DO UPDATE`.
Обновление выполняется только если бизнес-колонки действительно отличаются.

Удаление строк, отсутствующих в новом MDB, не выполняется. Это сознательная
политика первой версии: при чтении работающего MDB временное отсутствие строки
опаснее ложного сохранения старой строки. Удаления исправляются следующей полной
миграцией.

### 5.14. Пересчёт `operations`

Перед частичным пересчётом программа гарантирует наличие индекса:

```sql
CREATE INDEX IF NOT EXISTS operations_payer_seller_idx
ON bergapp.operations (id_payer, id_seller);
```

При количестве затронутых пар до 500 текущая реализация вызывает процедуру для
каждой пары:

```sql
CALL bergapp.calculate_and_save_operations(id_payer, id_seller);
```

Для каждой пары удаляются её старые операции и рассчитываются новые.

Если пар больше 500, выполняется полный пересчёт:

```sql
CALL bergapp.calculate_and_save_operations();
```

Текущий порог 500 является начальным. Замеры показали, что его стоит уточнить:
при достаточно большом количестве пар единичный полный set-based расчёт может
оказаться быстрее последовательности отдельных вызовов.

Для диагностики пересчёт можно отключить:

```bash
--skip-recalculate
```

В штатном режиме отключать его нельзя, иначе `bergapp.operations` перестанет
соответствовать исходным таблицам.

### 5.15. Обновление materialized views

Если найдены реальные изменения, последовательно обновляются:

```sql
REFRESH MATERIALIZED VIEW bergapp.payers;
REFRESH MATERIALIZED VIEW bergapp.sellers;
REFRESH MATERIALIZED VIEW bergapp.invoices;
REFRESH MATERIALIZED VIEW bergapp.counterparties;
REFRESH MATERIALIZED VIEW bergapp.balances;
REFRESH MATERIALIZED VIEW bergapp.debt_invoices;
```

Для диагностики refresh можно отключить:

```bash
--skip-refresh-views
```

Если изменений нет, пересчёт операций и refresh представлений не выполняются.

### 5.16. Транзакционность применения

В одну транзакцию PostgreSQL входят:

- создание staging-таблиц;
- загрузка staging;
- удаление нестабильных строк из staging;
- upsert в `bergauto`;
- пересчёт `bergapp.operations`;
- refresh materialized views;
- запись состояния и журнала дельты.

Если любой из этих этапов завершается ошибкой, изменения локальной базы
откатываются целиком.

Чтение кандидатов из MDB происходит до начала этой транзакции. MDB не имеет
общего транзакционного снимка с PostgreSQL.

## 6. Состояние синхронизации

Инкрементальный режим создаёт схему `berg_sync`.

### 6.1. `berg_sync.state`

Таблица содержит одну строку:

- `baseline_id` — идентификатор последней полной основы;
- `delta_seq` — номер применённой дельты внутри baseline;
- `source_mdb` — путь к последнему MDB;
- `date_offset_hours` — используемая коррекция дат;
- `source_max_ids` — максимальные ID источника;
- `updated_at` — время обновления состояния.

Если состояния ещё нет, первый инкрементальный запуск создаёт baseline вида:

```text
2026-09-19-135344-local-full
```

После полной миграции схема `berg_sync` удаляется, поэтому новый baseline будет
создан автоматически.

### 6.2. `berg_sync.patches`

Для каждого успешного запуска сохраняются:

- `patch_id`;
- `baseline_id`;
- последовательный номер дельты;
- путь к MDB;
- начало периода;
- количество вставок и обновлений по таблицам;
- количество финансовых пар;
- время создания.

Пример идентификатора:

```text
2026-09-19-135344-local-full-delta-0001
```

Даже запуск без изменений создаёт запись и увеличивает `delta_seq`. Файловый
пакет для отправки на хостинг в текущей версии не формируется.

## 7. Сравнение полной и инкрементальной миграций

Проверка выполнялась двумя способами:

1. полная миграция последнего MDB;
2. полная миграция предыдущего MDB и последующее применение последнего MDB как
   дельты.

Полностью совпали:

- все таблицы, кроме ожидаемых удалений;
- `bergapp.operations`;
- все materialized views.

В инкрементальной базе остались три заявки, удалённые из нового MDB. На них не
ссылались счета, поэтому расчётные данные совпали. Это подтверждает заявленную
политику: первая версия дельты не применяет удаления.

## 8. Измеренная производительность

Замеры зависят от оборудования, состояния кэша и конкретных данных, но дают
представление о текущих узких местах.

### 8.1. Полная и инкрементальная обработка

На использованных MDB:

```text
полная миграция последнего MDB:            около 1 мин 28 сек
инкрементальная обработка с расчётами:      около 1 мин 30 сек
инкрементальная без operations и views:    около 34 сек
```

Первая версия инкрементального режима ориентирована прежде всего на уменьшение
объёма изменяемых данных и будущей передачи на хостинг. Из-за полного refresh
представлений она пока не гарантирует меньшего общего времени, чем полная
миграция.

### 8.2. Materialized views

Измеренное время полного refresh:

```text
payers             0,171 сек
sellers            0,151 сек
invoices          22,154 сек
counterparties     0,645 сек
balances           0,809 сек
debt_invoices      0,527 сек
итого             около 24,46 сек
```

Основное узкое место — `bergapp.invoices`.

### 8.3. Индекс финансовых пар

Для пересчёта 132 пар:

```text
без индекса:       около 10,94 сек
с индексом:        около 0,22–0,32 сек
```

Полный пересчёт:

```text
без индекса:       около 19,39 сек
с индексом:        около 20,76 сек
```

Индекс немного замедляет массовую вставку полного расчёта, но значительно
ускоряет частые частичные пересчёты.

## 9. Рекомендуемый эксплуатационный цикл

Начальный вариант расписания:

```text
ночью:
  полная миграция MDB → локальный PostgreSQL

каждые 30 минут:
  обычная инкрементальная выгрузка

каждые 4 часа:
  инкрементальная выгрузка с --full-customers
```

Примеры команд:

```bash
# Обычная дельта
dotnet run --project . -- \
  --mdb C:/WORK/BERG/Berg/DB/bergauto.mdb \
  --incremental \
  --pg-database bergdb

# Расширенная проверка Customers
dotnet run --project . -- \
  --mdb C:/WORK/BERG/Berg/DB/bergauto.mdb \
  --incremental \
  --pg-database bergdb \
  --full-customers
```

Следующий инкрементальный запуск не следует начинать, пока предыдущий ещё
работает. Advisory lock не допустит одновременного применения, но второй процесс
успеет заранее прочитать кандидатов из MDB и будет напрасно расходовать ресурсы.

## 10. Ограничения текущей реализации

Инкрементальная выгрузка может временно не обнаружить:

- удаление строки;
- изменение старого документа за пределами периода и ID overlap;
- изменение старого клиента, не связанного с выбранными заявками, если не указан
  `--full-customers`;
- изменение `xSaldo`;
- логический откат MDB, при котором максимальные ID не уменьшились;
- согласованный снимок нескольких одновременно изменяемых таблиц MDB.

Эти расхождения должна исправлять регулярная полная миграция.

Текущая версия также не реализует:

- формирование переносимого файла дельты;
- отправку на хостинг;
- очередь недоставленных пакетов;
- повторные попытки доставки;
- подтверждённые удаления;
- инкрементальное обновление materialized views.

## 11. Критичные правила эксплуатации

1. Не менять `--mdb-date-offset-hours` между полной и инкрементальными
   выгрузками.
2. Не применять дельту к базе, созданной из более нового MDB.
3. Не использовать `--skip-recalculate` и `--skip-refresh-views` в штатном
   расписании.
4. Не считать инкрементальную выгрузку заменой периодической полной миграции.
5. После изменения схемы MDB сначала обновить `migration-schema.json` и выполнить
   полную миграцию.
6. При ошибке полной миграции повторить её целиком.
7. При ошибке инкрементальной миграции устранить причину и повторить запуск: её
   PostgreSQL-транзакция будет откачена.
